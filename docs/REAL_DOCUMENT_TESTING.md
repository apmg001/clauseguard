# Real-document testing

The evaluation harness (`scripts/run_eval.py`) scores detection on *synthetic*
cases, which validates the rules but says nothing about real-world extraction.
To close that gap honestly, ClauseGuard's extraction pipeline was run against a
genuine third-party invoice — not one generated by this project.

## Test document

A real, digitally-generated **GST tax invoice** (Indian Institute of Technology
Roorkee, invoice `A00001`): five line items (Bluetooth, Speaker, Keyboard,
Mouse, Monitor) with per-line CGST/SGST and a ₹12,185.86 total.

Reproduce with:

```bash
python scripts/inspect_document.py path/to/invoice.pdf
```

## Result: both deterministic tiers failed (and that is the finding)

The cascade tried the layout-aware tier, then the rule-based text tier, and both
correctly failed rather than emitting a wrong `Invoice`:

The pipeline degraded gracefully and reported *why* — which is the point of the
exercise.

## Root-cause analysis

Four concrete, real-world reasons this document defeats deterministic extraction:

1. **Collapsed table geometry.** `pdfplumber` recovered the whole item table as a
   single 2×1 cell — the PDF has no ruling lines / column boundaries for the
   geometry-based tier to latch onto, so it saw no real table.
2. **Doubled-glyph header.** The header row extracted as
   `IItteemm GGSSTT QQuuaannttiittyy ...` — the invoice renders bold/overlapping
   glyphs that the text layer duplicates, so no column name matches an alias.
3. **Different schema.** Columns are `Item / GST Rate / Quantity / Rate / Amount
   / CGST / SGST / Total` — there is no SKU (the item name *is* the description),
   no line-number column in the expected form, and tax columns the domain model
   does not represent.
4. **Unlabelled headers.** `Invoice No A00001` and `Billed By` (no colons),
   rather than the `Invoice-ID:` / `Vendor:` shape the deterministic header
   parser expects.

## What this validates

- **The tiered architecture is the right design.** Deterministic parsing has a
  hard ceiling on layout variety; this document is squarely past it. That is
  precisely why extraction is tiered and why the **LLM tier** (`LLMInvoiceExtractor`)
  exists — reading a document whose layout defeats rules is exactly the
  "genuine language/layout ambiguity" the project reserves for a model.
- **Fail-loud worked.** No wrong `Invoice` was produced; the system reported an
  actionable reason instead.

## Honest next steps to handle documents like this

- **Wire the LLM tier into the cascade** (needs a provider, e.g. local Ollama).
  This is what Tier B was built for; grounding still guards against hallucinated
  numbers.
- **A layout model** (e.g. LayoutLMv3 / Donut) for coordinate-aware table
  recovery when there are no ruling lines.
- **Extend the domain model** to represent tax lines (GST/CGST/SGST) and
  item-as-description schemas.

Deterministic tiers cover clean, structured digital PDFs; documents like this GST
invoice are the frontier the roadmap items above address.
